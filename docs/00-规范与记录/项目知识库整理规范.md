# 项目知识库整理规范

> 适用范围：本仓库的 README、AGENTS.md、CLAUDE.md、docs、实验路线记录、外部 baseline 复现文档和推进记录。
> 2026-10-02 更新：分层表与同步规则改到 V5 分块结构；新增 §6 多会话并行协议（多个 AI 会话同时工作时保持文档统一）。

本规范用于把项目管理从“不断追加记录”收敛为“入口清楚、路线分层、状态可追踪”的工程化知识库。核心原则是：事实写到最贴近事实的位置，入口只做导航，推进记录只做按时间倒序的变更凭证。

## 2. 变更同步规则

- 训练、评估、loss、dataset、pipeline、Slurm 或配置发生变化时，先更新对应代码目录 README 或路线文档，再更新推进记录。
- 外部论文 baseline 不写入 V3 内部优化路线，统一进入 `docs/paper_reproduction/` 和 `external_baselines/`。
- 不同路线、数据版本、评估集必须分开记录；可以在总纲中横向总结，但不要在执行表里混写（V1 / V2 / V3 / V5 各线同理）。
- V5 实验结果写所属块的实验跟踪，同时更新该块 README 的「当前状态」；改变了跨文档事实时按 §6.5 登记表同步。
- 新实验结果优先进入路线日志或状态表；只有路线定位改变时才更新 `docs/实验设计总纲.md`。
- 点云回构、插值和 CFD-Post/Fluent 展示属于可视化交付链，不能替代同点定量评估。

## 3. 推进记录格式

`docs/02-推进与变更/代码修改与实验推进记录.md` 必须保持越新越靠上。新记录插入在文件说明块和第一条历史记录之间。

每条记录至少包含：

- 本次主要修改
- 对应代码/文档
- 推进到实验步骤
- 当前状态判断

建议标题格式：

```markdown
## YYYY-MM-DD｜主题 · 动作 · 状态
```

状态应写清楚 `已提交`、`训练中`、`TIMEOUT`、`完训`、`No-Go`、`待验证` 等，不使用“最近”“刚刚”等相对时间。

## 4. 清理检查清单

每次整理文档或收尾前，至少检查：

- `AGENTS.md` 是否只保留硬规则，没有变成历史流水账。
- `docs/README.md` 的入口是否能带新人找到总纲、任务 A、推进记录、外部 baseline 和汇报材料。
- 同一实验状态是否只在一个主文档中维护，其他位置只做链接或摘要。
- 已完成的交接文档是否归档到 `_archive/`，并在当前路线文档中保留最终结论。
- 进度记录是否位于文首，且包含四个必需部分。
- 文档中是否残留 `今天`、`昨天`、`最近`、`上周` 等相对时间。
- 入口与各块 README 的状态是否与运行产物一致（作业是否真的在跑 / 已完成、在用的发布包与服务版本、数据版本）；§6.5 登记表里的事实在各副本处是否一致。
- 占用的共享资源是否已告知、释放后是否已撤销告知（§6.2）。

## 5. 不应做的事

- 不因为整理文档而移动或删除 `data_new/`、`outputs/`、`stl_data/` 等大数据或证据目录。
- 不把外部 baseline 的训练状态写成 V3 内部消融。
- 不把失败路线删除；应写成历史证据、No-Go 原因或后续边界。
- 不在 `AGENTS.md` 里堆单次实验历史。

## 6. 多会话并行协议（2026-10-02）

本仓库常同时开着多个 AI 会话（Claude Code / Cursor / codex）做不同课题，每个会话只熟悉自己那块。为了不让文档分叉，每个会话都遵守下面几条。完整做法见 skill `lab-docs-engineering` 的 `parallel-sessions.md` 与 `sync-audit.md`（本体 `~/.cursor/skills/lab-docs-engineering/`，Claude Code 经 `~/.claude/skills/` 加载同一份）。

### 6.1 开工检查

开始任务时读：所属块 README「当前状态」与跟踪最新节、推进记录文首 3–5 条、§6.5 里相关事实的**规范位置**（不要从副本处读现状）。再看谁在动什么：`git status`、最近 3 小时改过的文档、`squeue -u cy`（`export PATH=/public/slurm/bin:$PATH`）。

### 6.2 跨线影响告知

占用别人也会用的资源（§6.6），或新产物依赖另一条线的文件（链接它的缓存、读它的中间结果）时，在**受影响块的 README** 追加一条带日期的告知：谁、何时起、预计到何时、占用 / 依赖了什么、对方不要做什么。只追加，不改对方其他内容；释放后改为「已释放（日期）」。

### 6.3 收尾同步（任务完成或阶段性停下时必做）

1. 本块跟踪：结果、作业号、证据路径。
2. 本块 README「当前状态」：改到现状，标题日期随之更新。
3. 跨文档事实：先改 §6.5 的规范位置，再逐个改副本（副本写一句话 + 链接）。
4. 推进记录文首一条（事实已写在跟踪里时写指针条目）。
5. 用户本轮的决定（含「暂不做」「先不动」）写进相关状态处，注明日期与「用户决定」。
6. 撤销 / 更新跨线影响告知。

### 6.4 编辑礼仪

- 定点替换，不整文件重写，不顺手统一格式。
- 文件 30 分钟内被别的会话改过：重读再改，能追加就只追加。
- 自己的块直接改；别的块只追加带日期、带依据的补记（「据 git / 进程 / 产物 YYYY-MM-DD HH:MM 核查」）。
- 不回滚别人的改动；认为有错先用产物核实。
- 已结束的小节、用户裁定原文、带日期的报告、旧日志条目不改正文，在其后加「后续状态（YYYY-MM-DD 补记）」。
- 文档与产物冲突时以产物为准（运行产物 > 调度器 / 进程 / 服务 > git > 跟踪 > 汇总文档 > 记忆）。
- 不用 raw HTML 注释与引用式链接定义（渲染器不支持）；文档统一写北京时间（master 系统时间是美西时间）。

### 6.7 全量同步

用户说「把文档更新到最新 / 全量同步」，或开工检查发现入口与产物有 2 处以上对不上时，按 skill 的 `sync-audit.md` 做一次：先建事实表，分清活文档与快照，扫过时说法，逐条用产物核实，定点修改，修结构错位，补推进记录，汇报改了什么、发现的错误、有意没改的、需要用户决定的。
