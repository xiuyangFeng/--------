# WSS 部署工具：架构评审与优化路线（2026-09-20）

> 对象：`wss_deploy/`（v0.5，约 7.9k 行 Python + JS，含三套 three.js 查看器）与[框架与计时文档](./WSS_部署演示工具_从STL到峰值WSS_整体框架与计时_2026-09-17.md) §14–§17 及 2026-09-20 体场接入。
> 性质：只读评审 + 路线建议，本轮未改任何代码。证据以 `文件:行` 给出，行号对应 2026-09-20 工作区（分支 `codex/clean-initial-commit`）。
> 立场：以"这个工具要作为软件持续交付三年、权重会换、字段会加、客户端会多"为前提审视，而不是以"演示能跑"为前提。

## 0. 一句话结论

工具已经从"演示"长成了"准产品"：合同校验、来源记录、人工确认、安全边界都比同类实验室工具严格得多，这是它的信用来源，重构时一样都不能丢。但骨架仍是 P1 那条"一个函数串到底 + 一个进程包打天下"的形态：接下来每加一种模型族、一条时间轴、一个客户端，都会在同一个 `stage_b`、`JobManager`、`TEMPLATE` 里再开一条 if 分支。下一阶段的核心不是再加功能，而是把四样东西提成一等公民：

1. **冻结特征库**（`wss_features`）：发布包不只冻结权重，也冻结"STL → 特征"的程序；
2. **类型化运行记录**（`RunRecord`）：一份真相，其余文件都是派生视图；
3. **模型族适配器**：编排器对 WSS / 体场 / 未来的多帧一无所知；
4. **内容寻址的几何资产**（`Geometry`）：人工确认过的中心线与命名是最贵的产物，要可复用、可回流。

做完这四件事，多帧、多场、换权重、纵向对比、外部 API 都是顺手的事；不做，它们每一件都要再写一遍胶水。

## 1. 做对了什么（重构时保留）

- **失败即关闭的合同**：发布包逐文件 SHA256 校验与模型配置合同（`registry.py` `_verify_package` / `_contract`）；置信度门控只在独立验证 profile 存在时放行（`centerline.py:54-125` `evaluate_confidence_gate`）；比较接口口径不一致时拒绝给差值（`comparison.py`）；人群分位只认 cv3 折外分布（`reference.py`）。"不把没验证过的东西伪装成能力"贯彻得很彻底。
- **完整来源链**：`run_manifest.json` 记输入哈希、权重哈希、代码提交、参数、映射历史、导出哈希；重跑前旧结果归档到 `history/`；`run_identity` 把同输入同模型同参数的运行绑成稳定身份。
- **人在回路**：出口命名先建议后确认，三个互换按钮保证拓扑一致；单位显式确认；自动路径永远可被人工覆盖并重算。
- **安全边界**对一个标准库 HTTP 服务而言相当完整：会话 + CSRF + Origin 校验、路径包含检查、CSP、上传上限、只开放白名单文件。
- **结果信封**（`fields` / `time_axis` / `results`，`schema.py`）已为多场多帧预留描述层；CLI 与服务共用同一条管线。
- **测试文化**：99 个测试覆盖合同、迁移、比较、参考、体场几何，py_compile 与 `node --check` 进验收。

## 2. 结构性问题（架构层）

### 2.1 部署包依赖训练库的私有符号与实验脚本，且靠模块级全局变量传参

证据：

- `geometry.py:8-15`：从 `training_wss_min.tools.deployment_stl_simulation`（验证工具脚本）取 `sample_surface` / `FINE_MAP`，从 `deployment_geometry_sensitivity`（实验脚本）取 `taubin_smooth`，从 `wss_v5.views.*` 取私有的 `_Tree`、`_unit_rows`；`centerline.py:13` 取 `_semantics`；`volume_geometry.py:17` 取 `_murray_shares`。
- `geometry.py:18` 在 import 时改写 `wall_flowref_v1._CAPFIT_RULE_OVERRIDE`；`geometry.py:60-70` 每次调用再设置/恢复同一个全局。`jobs.py:95-98` 明确因此用 `_stage_b_lock` 把整个 B 段串行化。
- 训练代码日常在改；队列运行期间改 `training_wss_min/*.py` 会让整条训练队列中止，这一点已有记录。

后果：

1. **同一发布包指纹下，特征代码可以悄悄变化。** 发布包只冻结了权重与统计，没有冻结"把 STL 变成 27 维特征"的程序。`run_manifest` 记的是整个仓库的 git commit（`schema.py:229-236`），它每天都变：既不能证明特征程序没变，也不能阻止用变了的特征程序跑旧权重。
2. 线程不安全的全局状态迫使 B 段完全串行，GPU 推理无法与另一例的 CPU 特征构建并行。
3. 训练侧任何重构（改私有函数签名、挪脚本）都会直接打断部署。

改法：抽出 **`wss_features/`**（独立包，或放进发布包内的 `code/` 目录）。要求：纯函数、无全局状态、`capfit_rule` 作为参数传入、带 `FEATURE_CONTRACT_VERSION`。`release.json` 声明它依赖的特征合同版本与代码哈希；`Release` 加载时校验；`run_manifest` 记特征合同哈希而不是仓库 commit。训练侧继续用自己的实现，发布时把对应版本"冻结拷贝"进特征库并跑逐位一致性测试——现有 KANG_YONG 新旧链路 R² 0.97 的做法正式化为自动测试。

### 2.2 `stage_b` 是上帝函数，`meta` 字典是事实上的数据模型，且被复制了四份

证据：

- `pipeline.py:80-260` `stage_b` 约 180 行：加载、平滑、重采样、特征、推理、质量、指标、插值、为查看器整理中心线数组、两次读 `job.json` 取映射历史与病例元数据（`pipeline.py:162,179`，管线层反向读服务层记录）、拼一个 40 余键的 `meta`、写 npz/csv/vtp/html、写 manifest。`volume_pipeline.stage_b_volume` 复制了其中大半。
- `meta` → `summary.json`（全量，`pipeline.py:245`）→ `job["summary"]`（`jobs.py:884-892` 白名单子集）→ `report.html` 内嵌（`report.update_html_meta`）→ `run_manifest.json`（`schema.build_run_manifest` 再投影）。四份拷贝，键集各不相同。
- 兼容层在蔓延：`comparison.py` 近百行 `_first_map` / `_first_value` 在新键、旧键、`metadata.*` 之间试探；`report._report_schema_metadata` 为旧报告补 `fields`；`jobs._recover_legacy_release` 甚至用正则从 `report.html` 里抠元数据。

改法：

- 定义类型化领域对象（`dataclass` 即可，不必上 pydantic）：`InputAsset`、`Geometry`（clean STL + atlas + 确认映射）、`FeatureSet`、`FieldSet`、`Statistics`、`RunRecord`。管线 = 纯步骤的组合，每步签名明确；导出器（npz / csv / vtp / html / manifest）各自消费 `RunRecord`，不再手拼字典。
- **一份真相 + 派生视图**：`RunRecord` 落盘为 `run.json`（schema v2）；`summary.json`、报告内嵌、`job.summary` 全由它派生，派生函数可单测。
- **迁移而不是兼容**：加 `migrate(record) -> v2`，旧文件磁盘不动，加载时一次升级；所有消费者只读 v2。"旧配置逐位不变"的硬要求针对训练配置，不针对部署结果文件。
- 统计量按 §15.2 的合同做成结构：`(field, support, weighting, aggregation, time_window)` 五元组显式声明，点云 p99 与面积加权 p99 就是两个不同的五元组，而不是两组键名。

### 2.3 模型族靠 if 分支分发，合同里写死了 step 1162

证据：`pipeline.py:83` `if target == "pressure_velocity": return stage_b_volume(...)`；`infer.py:54,100,130` 三处 `if self.is_volume`；`registry.py:151` 以 `release == "X5D_v51_5seed_20260916"` 补默认时间轴，`registry.py:156,184,225` 三处写死 `step != 1162 or time_s != 0.21`。用户已声明长期约束：权重持续替换、多帧将至、速度/压力/WSS 同任务。

改法：**模型族适配器**。`release.json` 声明 `family`；代码里一个注册表 `FAMILIES = {"wss_wall_v1": WallWssAdapter, "pf6_vf6_volume_v1": VolumeAdapter, …}`，每个适配器实现四个方法：`build_inputs(geometry) -> case`、`predict(models, case) -> FieldSet`、`statistics(FieldSet, geometry) -> Statistics`、`exporters()`。编排器对族一无所知；合同校验（允许的帧、字段、归一化）由适配器声明，注册表只做通用校验（哈希、路径、清单）。`FieldSet` 的数组统一为 `[T, N, C]`，单帧就是 T=1；时间轴是数据维而不是元数据备注，TAWSS / OSI 将来只是 `Statistics` 里沿 T 轴的归约。

### 2.4 任务系统：全量常驻内存 + JSON 文件 + 全局锁 + 与 HTTP 同进程

证据：

- `jobs.py:116` `_load` 启动时把每个 `job.json` 整份读进 `self.jobs`，其中 `a`（stage_a 快照）含最多 18k 面的预览网格与中心线折线（`pipeline.py:18` `_preview_surface`）；`jobs.py:258-291` `_snapshot(detail=True)` 每次 `GET /api/jobs/<id>` 在全局锁内 `copy.deepcopy` 这份结构；前端每 2 s 轮询一次（`static/app.js:573`）。工作器的 `_progress` 事件也要拿同一把锁，会被轮询的深拷贝阻塞。10 个任务已 185 MB 磁盘；千级任务时内存与启动时间不可接受。
- `jobs.py:354,359` `list` / `query` 全表线性扫描；`stage_a.json` 存绝对路径（`ingest.py:268`），`rerun` 用字符串替换修补（`jobs.py:692-730` `_replace_paths`）；任务目录不可搬迁。
- 两个线程工作器 + 一把 B 段锁；A 段（VMTK 子进程 + numpy）与 B 段（GPU）不区分资源；上传体最大 128 MiB 整体读入内存（`server.py:118-124`）再交给 `email` 解析（`server.py:205`）。
- `pipeline.py:117,126` 按任务改 `torch.set_num_threads`（进程全局）；发布包缓存按 (id, device, seed_count) 无限增长（`registry.py:283,395-420`）。

改法（按顺序）：

1. **存储**：SQLite（WAL）存任务 / 事件 / 病例元数据，大对象（stage_a 快照、预览网格）落盘按需读；路径一律相对任务根。
2. **API 与工作器分进程**：`api`（FastAPI）只做校验与读写数据库；`geometry-worker ×N`（CPU：ingest → centerline → 建议）与 `model-worker ×1/GPU`（特征 → 推理 → 统计 → 导出，模型常驻 + LRU 驱逐）。队列就是 SQLite 表（`status='queued' ORDER BY priority, created` + 乐观锁），不需要 Redis / Celery。线程数、设备成为 worker 的进程级设置。
3. **进度推送**用 SSE（`text/event-stream`）替代 2 s 轮询；`GET /jobs/<id>` 只回轻量状态，`/jobs/<id>/geometry` 带 ETag 单独取。
4. 上传走流式落盘（临时文件 + 边读边哈希），幂等键防双击重复建任务；`/api/jobs/batch` 真正被前端使用（服务端已实现）。

### 2.5 中心线跨环境子进程

证据：`centerline.py:151-158` 每例 `subprocess.run([VMTK_PYTHON, "-m", "vessel_geom.cli", …])`；`paths.py` 写死 `~/.conda/envs/GNN_vmtk/bin/python`。每例付一次解释器 + VTK 导入的冷启动，Windows 打包不可行。

改法：短期把 `vessel_geom` 做成**常驻工作进程**（stdin/stdout JSON 协议或本地 socket），启动一次反复用，顺带把"VMTK 前抽稀到约 1 mm"做进去；中期合并环境（conda-forge vmtk + pip torch，`conda-lock` 锁定）并重跑 50 项解析解测试 + 34 例回归；打包走容器，Windows 用 WSL2 容器。

### 2.6 三套 three.js 查看器与字符串拼报告

证据：`report.py:162-377` `TEMPLATE`（壁面 WSS，约 210 行内联 JS）、`volume_report.py:126` `TEMPLATE` + `static/volume_viewer.js`（体场，406 行）、`static/app.js:495` `createViewer`（出口确认）各自实现相机、拾取、色标、剖切、标签；报告用 `str.replace`（`report.py:157`，`volume_report.py:119`）注入 600 KB three.js 与 base64 数组，每份 4–6 MB。

改法：一个 `static/viewer/` 模块库（scene、colormap、picking、clipping、colorbar、slice、labels），工作台与离线报告共用；报告仍单文件（用户硬要求：能发微信、双击打开），但由模板引擎生成，数据块用 float16 + 量化索引（体积可减半）；three.js 只在报告里内联一次，工作台走静态文件。

## 3. 目标架构

```
┌─────────────── 客户端 ───────────────┐
│ 工作台 SPA │ CLI │ REST（科研平台/PACS）│ 离线单文件报告
└──────┬─────┴──┬──┴────────┬──────────┘
       ▼        ▼           ▼
┌──────────── API 层：FastAPI，/api/v1，OpenAPI，SSE ────────────────────────┐
│ users/sessions · patients/scans/geometries/runs · jobs · releases · compare │
└──────┬─────────────────────────────────────────────────────────────────────┘
       ▼
┌──────────── 领域层（纯 Python，无 IO）────────────┐   ┌──── 存储 ────┐
│ 实体：Patient → Scan → Geometry → Run → Artifact │   │ SQLite (WAL) │
│ 合同：Release · FeatureContract · FieldSet[T,N,C] │   │ CAS blob 区   │
│ 模型族适配器注册表：wss_wall / pf6_vf6 / …        │   └──────────────┘
└──────┬───────────────────────────────────────────┘
       ▼
┌──────────── 执行层（独立进程）──────────────────────────────────┐
│ geometry-worker ×N（CPU）：ingest → centerline（常驻 VMTK）→ 建议 │
│ model-worker ×1/GPU：特征 → 推理 → 统计 → 导出（模型常驻，LRU）   │
└──────┬─────────────────────────────────────────────────────────┘
       ▼
┌──────────── wss_features（冻结特征库，版本化，无全局状态）────────┐
└───────────────────────────────────────────────────────────────────┘
```

实体关系要点：

- **Geometry 是人工验证过的资产**，键 = clean STL 哈希 + 入口 + 中心线程序版本 + 确认映射。它是整条链里最贵（人工分钟级）也最有复用价值的东西，今天却只是 `job["mapping"]`，重跑靠复制目录。提成实体后：换模型重跑不再复制、纵向对比按 Patient → Scan 走、命名修正可以回流训练侧 atlas（8 例出口命名互换那类问题以后由工具发现）。
- **Run = Geometry × Release × 参数**，`run_identity` 天然成为缓存键。缓存键应排除 `device` / `threads`（执行细节，CPU 与 GPU 数值差 0.05 Pa），manifest 照记。
- **Job 只是产生 Run 的执行日志**，可以失败、取消、重试，不承载任何科学结论。

## 4. 框架层（工程基础设施）

| 项 | 现状 | 建议 |
|---|---|---|
| 依赖与打包 | `PYTHONPATH` 指向单体仓库；无 `pyproject`、无锁文件、无镜像 | `wss_deploy` 与 `wss_features` 各自 `pyproject.toml`；`conda-lock` / `pip-tools` 锁定；Dockerfile 双阶段（CPU 版约 1 GB、CUDA 版约 3 GB）；`wss-deploy` 命令入口 |
| 配置 | `paths.py` 写死路径 + 环境变量 + argparse 混用 | 单一 `Settings`（TOML + 环境变量覆盖），启动即校验并在 `/healthz` 回显 |
| 数据库 | JSON 文件 + 内存字典 | SQLite（WAL）+ 迁移脚本；千级任务、毫秒级检索 |
| 队列 | `queue.Queue` + 版本号 | SQLite 队列表（优先级、owner 公平、幂等键防重复上传） |
| 进度 | 2 s 轮询 + 全量快照 | SSE 事件流；轻重接口分离 |
| Web 框架 | 标准库 `BaseHTTPRequestHandler`，手写 multipart | FastAPI + pydantic 模型 = 自动 OpenAPI、请求校验、流式上传；现有安全策略照搬为中间件 |
| 前端 | 单文件 IIFE + 手写 DOM + 三套查看器 | 按模块拆分（api / state / views / viewer），共用 viewer 库；暂不引框架，但要有构建脚本与 `node --check` 之外的最小测试（Playwright 冒烟） |
| 可观测 | 文本日志 + 诊断编号 | 结构化 JSON 日志；`/healthz`（GPU、发布包、队列深度、磁盘）；每段耗时入库，可出"最近 100 例各段耗时"图；任务目录保留策略与配额 |
| 测试 | 99 个合同/单元测试；1 个 HTTP 测试；34 例验收手动 | 加三层：① 黄金回归（固定 STL → p99 / max / 分支表在容差内，绑定发布包指纹与特征合同哈希，CI 必跑）；② 端到端 HTTP（假发布包）；③ ingest 的性质测试（随机网格不崩）。34 例验收脚本化，可一键复跑出对比表 |
| 缓存 | 无；同 STL 重复上传全量重算 | 内容寻址：`store/<sha256>/{clean.stl, centerline/, features_<contract>.npz}`；A 段与特征跨任务、跨发布包复用（换模型重跑从 30 s 降到推理的 6 s） |
| 多用户 | 会话即所有者，清 cookie 即失联 | 本地用户表（用户名 + 口令哈希 + 角色），任务归用户；管理员可看全部；共享链接 |

## 5. 功能层（按价值排序）

1. **确认页变成标注飞轮**。`mapping_history` 已经存了"建议 vs 确认 vs 置信度"，这就是独立标注集。加导出脚本 → 定期生成校准 profile（Brier / ECE 已在 `confidence_audit.py`）→ 写进发布包 → 门控才有放行的可能。今天的门控代码是一条永远走不到的路径，飞轮让它活过来；同时也是训练侧 atlas 命名修正的来源。
2. **几何资产与内容寻址缓存**（§3），直接带来：换发布包秒级重跑、同患者两次扫描对比不再复制目录、离线 CLI 与网页共用缓存。
3. **`FieldSet[T,N,C]` 与族适配器**（§2.3），是 TAWSS / OSI、速度 + 压力 + WSS 同任务、时间滑块的前提。
4. **OOD 与人群刻度尺落地**：`geometry_reference` 与 `population_reference` 的校验逻辑已写好，但没有任何发布包声明它们。补两个生成脚本：从 train136 几何分布生成范围 profile、从 cv3 折外预测生成 p99 分布 profile，随下一个发布包一起冻结。
5. **一页纸 PDF**：现有打印样式已接近；用 headless Chromium（Playwright）在服务端出 PDF，避免引入 reportlab 重画一遍。
6. **对外 REST / OpenAPI**：FastAPI 顺带得到；补 API token 与幂等上传，即可接科研平台或 PACS 中间件。
7. **报告瘦身与共用查看器**（§2.6）。
8. **CPU 路径**：三 seed 快速模式已存在；线程数变成 model-worker 的进程级设置；内判测试改批处理（§6）。
9. 桌面壳（pywebview）与 Windows：留到容器打包稳定之后。

## 6. 立刻可做的小修（不等重构）

## 7. 路线建议

| 阶段 | 内容 | 验收 |
|---|---|---|
| **R0 止血（1 周）** | §6 小修；黄金回归测试上 CI；34 例验收脚本化 | 同发布包 p99 逐例差 ≤ 1e-4；CI 绿 |
| **R1 骨架（3–4 周）** | `wss_features` 抽出并逐位对齐；类型化 `RunRecord` + 迁移；族适配器；SQLite + CAS；API / worker 分进程；SSE | 34 例回归与 R0 逐位一致；换发布包重跑 ≤ 10 s；千任务列表 < 50 ms |
| **R2 产品（3–4 周）** | FastAPI + OpenAPI；用户表；共用 viewer 库；报告瘦身；PDF；OOD / 人群 profile 生成脚本；标注导出 | 两人并发不互阻；报告 ≤ 2.5 MB；profile 随发布包冻结 |
| **R3 打包（2 周）** | 环境合并 + 锁；容器；Windows / WSL；桌面壳可选 | 干净机器 30 分钟内跑通一例 |

每一步都要求：旧任务目录仍可读、34 例回归数值不变、`run_manifest` 能解释任何一份历史结果。

## 8. 不建议做的事

- 不上 Celery / Redis / Kubernetes：单机 SQLite 队列足够，多引入的运维成本远大于收益。
- 不把前端重写成 React / Vue 大工程：先拆模块与共用查看器，框架决策留到 API 稳定后。
- 不把训练库并入部署包：方向相反，抽冻结特征库出去。
- 不用 `acceptance_test34` 拟合置信度 profile（现有代码已明确拒绝）；用飞轮攒独立集。
- 不为多帧提前做 UI；先把 `FieldSet` 的 T 轴做实，UI 随第一个真实多帧发布包出现。
